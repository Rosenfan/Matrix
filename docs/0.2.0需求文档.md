# Matrix V0.2.0 重新定义

## 一句话定义

Matrix V0.2.0 不再改造原有软件开发工作流，而是在完整保留 Matrix 0.1.3 的基础上，新增独立的 `matrix-find`：

> matrix-find 根据用户的真实目标，寻找、改造或生成最合适的完整工作流，并将它作为一个可调用、可复用、可替换局部能力的 Workflow Package 交付给用户。

## 一、产品边界

### 原 Matrix 保持不变

以下 0.1.3 功能属于兼容性红线：

- `full` 软件开发工作流；
    
- `hotfix` 工作流；
    
- `tweak` 工作流；
    
- Open、Design、Build、Verify、Archive 五阶段；
    
- Prim 与 Arch 编排方式；
    
- `matrix/change/v2` 状态结构；
    
- Return、Abort、恢复、证据和归档机制；
    
- 原有 Matt Skills 能力组合；
    
- 原有 CLI 命令、输出语义和历史 Change 兼容性。
    

V0.2.0 不将这些内容重构为通用 Profile，也不把非开发工作塞进原五阶段。

### matrix-find 是额外能力

matrix-find：

- 不替代 `$matrix`；
    
- 不修改原 Matrix 状态机；
    
- 不把自己当成用户最终需要的工作流；
    
- 不强迫所有行业使用 Open/Design/Build/Verify/Archive；
    
- 不因新增功能改变原软件工作流的行为。
    

两者的关系是：

```
Matrix 0.1.3
└─ 继续负责软件开发工作流

matrix-find
└─ 负责发现、生成、组装和交付其他工作流
```

## 二、matrix-find 真正解决的问题

用户通常只知道自己“想做什么”，并不知道：

- 完整工作流应该有哪些阶段；
    
- 每个阶段应该完成什么；
    
- 哪些步骤需要专业能力；
    
- 应该调用哪些 Skills；
    
- 找不到 Skill 时怎么办；
    
- 工作流不满意时如何局部修改。
    

matrix-find 负责将模糊需求编译成一个可执行工作流。

它不是单纯的 Skill 搜索器，而是：

- Workflow Finder：搜索现成工作流；
    
- Workflow Adapter：改造接近的工作流；
    
- Workflow Composer：组装阶段、步骤和能力；
    
- Workflow Compiler：生成 Agent 可调用的工作流入口；
    
- Workflow Maintainer：支持后续局部替换和版本升级。
    

## 三、完整用户流程

### 1. 澄清真实需求

用户提出第一个工作流需求后，matrix-find 进入需求澄清。

可以使用 `grilling` 类能力，但必须遵守：

- 只询问会改变工作流设计的问题；
    
- 不进行无止境提问；
    
- 明确目标、交付物、限制、参与者、时限、风险和完成标准；
    
- 区分一次性任务和需要长期复用的工作流。
    

输出为一份经过用户确认的 Workflow Brief。

### 2. 优先搜索完整工作流

搜索顺序必须是：

```
搜索完整工作流
→ 找到后评估是否直接可用
→ 不完全适合则进行改造
→ 完全找不到才从零生成
```

不能一开始就只搜索零散 Skills。

可能产生三种结果：

1. 找到可直接使用的工作流；
    
2. 找到接近的工作流，经过调整后使用；
    
3. 没有合适工作流，生成新的工作流。
    

### 3. 设计业务工作流

生成真正符合领域需要的阶段。

例如短视频工作流可以是：

```
选题
→ 调研
→ 脚本
→ 分镜
→ 拍摄
→ 剪辑
→ 质检
→ 发布
```

生日聚会工作流可以是：

```
需求确认
→ 邀请与统计
→ 场地和预算
→ 食物与活动安排
→ 执行准备
→ 当天协调
→ 费用确认与复盘
```

这些阶段不需要映射为 Matrix 原有五阶段。

### 4. 建立能力槽位

对每一个专业步骤定义能力槽位：

- 什么时候触发；
    
- 需要什么输入；
    
- 应该产生什么输出；
    
- 如何判断完成；
    
- 允许哪些副作用；
    
- 失败后的备用方案；
    
- 当前由哪个 Skill、Agent 或人工步骤负责。
    

### 5. 补齐能力

能力来源按以下顺序处理：

1. 已安装的本地 Skill；
    
2. 已知可信 Provider；
    
3. 使用 `find-skills` 搜索候选；
    
4. 对候选进行来源、权限、副作用和兼容性评估；
    
5. 没有合适能力时，使用 `skill-creator` 创建新 Skill；
    
6. 仍无法自动化时，明确保留人工步骤。
    

原则是：

> 先确定正确的工作流，再为工作流补齐能力。

### 6. 组装和验证

matrix-find 将阶段、能力、模板和验证标准组装成完整 Workflow Package。

交付前需要：

- 检查阶段和依赖是否完整；
    
- 检查是否存在无法完成的能力缺口；
    
- 模拟至少一条正常流程；
    
- 验证失败、退回和人工接管路径；
    
- 明确外部副作用和用户确认点；
    
- 确保 Agent 能正确识别下一步该做什么。
    

### 7. 用户确认并交付

用户确认后，matrix-find 完成工作流安装。

此后 matrix-find 退出，真正推进任务的是生成出来的工作流。

## 四、工作流的存在形式

每个工作流都是一个独立的 Workflow Package。

推荐目录：

```
.matrix/find/
├─ workflows/
│  └─ short-video-production/
│     ├─ SKILL.md
│     ├─ workflow.yaml
│     ├─ capabilities.yaml
│     ├─ skills-lock.json
│     ├─ skills/
│     ├─ templates/
│     ├─ evals/
│     └─ CHANGELOG.md
│
├─ runs/
│  └─ <run-id>/
│     ├─ state.json
│     ├─ events.jsonl
│     ├─ evidence/
│     └─ outputs/
│
└─ registry.json
```

各部分职责：

- `SKILL.md`：Agent 调用入口；
    
- `workflow.yaml`：阶段、步骤、依赖、Return 路径和完成标准；
    
- `capabilities.yaml`：步骤与能力槽位的绑定；
    
- `skills-lock.json`：Skill 来源、版本、提交 SHA 和内容 Hash；
    
- `skills/`：工作流专属能力；
    
- `templates/`：检查表、表格、文档等模板；
    
- `evals/`：工作流验证案例；
    
- `runs/`：每次实际执行产生的状态、事件和证据；
    
- `registry.json`：项目中的工作流索引。
    

工作流定义与运行数据必须分开：

```
Workflow Package = 可复用定义
Run = 某一次真实执行
```

因此不会再出现“对话中说已经归档，但项目里什么都没有”的情况。

## 五、Agent 如何调用工作流

生成的 Workflow Package 会被编译成对应 Agent 可发现的入口，例如：

```
.agents/skills/short-video-production/
.claude/skills/short-video-production/
```

用户可以直接表达：

```
使用 $short-video-production 制作一期关于露营装备的视频。
```

也可以通过自然语言让 Agent 推荐工作流：

```
我准备开始制作一个系列短视频，帮我选择合适的工作流。
```

matrix-find 负责生成和维护工作流；生成后的 Skill 入口负责推进实际业务。

## 六、多个工作流的选择规则

一个项目可以存在多个 Workflow Package。

选择优先级：

1. 用户明确指定的工作流；
    
2. 当前正在执行的 Run 所绑定的工作流；
    
3. 唯一且高置信度匹配的工作流；
    
4. 存在多个候选时，展示差异并让用户选择；
    
5. 没有合适工作流时，进入 matrix-find。
    

禁止根据模糊关键词静默切换工作流。

每个 Run 必须冻结：

- workflow ID；
    
- workflow version；
    
- package digest；
    
- capability bindings；  
    -开始时间和当前步骤。
    

即使工作流以后升级，旧 Run 也不能被静默改变。

## 七、工作流的优化与局部替换

每个阶段、步骤和能力槽位都必须有稳定 ID。

用户可以表达：

```
脚本写作这一步不满意，其他步骤不要动。
```

matrix-find 应能够：

1. 定位对应步骤；
    
2. 判断问题来自流程设计、提示、模板还是 Skill；
    
3. 搜索替代 Skill；
    
4. 优化现有 Skill；
    
5. 使用 skill-creator 创建新能力；
    
6. 只更新对应槽位；
    
7. 生成新的工作流版本；
    
8. 保留旧版本和变更记录。
    

工作流升级不应整体推翻：

```
v1.0.0
→ 替换 script-writing 槽位
→ v1.1.0
```

## 八、Matt Pocock Skills 的处理

Matt Skills 只是能力来源之一，不是 V0.2.0 的产品中心。

### 原 Matrix Arch

为了兼容 0.1.3：

- 保留原有 Matt 能力清单和 Arch 行为；
    
- 不因上游分类变化改写原工作流；
    
- 不增加新的前置配置要求；
    
- 不将用户调用型 Skill 自动嵌套进原阶段。
    

### 最新版本检测

执行 `matrix init` 或明确更新时：

1. 联网解析 Matt 当前最新稳定版本和最新提交；
    
2. 检查与原 Matrix Arch 能力合同的兼容性；
    
3. 下载当时最新的兼容版本；
    
4. 使用精确提交 SHA 安装；
    
5. 记录内容 Hash；
    
6. 安装失败或不兼容时完整回滚；
    
7. 不静默覆盖用户修改。
    

“使用最新版本”定义为：

> 安装或更新时获取最新兼容版本，安装后冻结，不在后续运行中自动漂移。

matrix-find 使用的 Matt Skills 与原 Arch 清单分开管理，不得反向改变原 Matrix。

## 九、明确不做的内容

V0.2.0 不做：

- 重写 Matrix Core；
    
- 将原状态 Schema 升级为 v3；
    
- 把 `full/hotfix/tweak` 改造成新 Profile；
    
- 用 `general.composed` 进入原五阶段；
    
- 让 matrix-find 直接执行所有业务；
    
- 将所有工作强制归纳为固定三阶段或五阶段；
    
- 找到 Skill 后未经确认直接安装；
    
- 静默执行外部写入、发布、付款或消息发送；
    
- 承诺首个版本覆盖所有行业；
    
- 仅靠对话声明工作流完成或归档。
    

## 十、V0.2.0 验收标准

### 原功能兼容

- 未修改的 0.1.3 原测试必须全部通过；
    
- 当前基线为 72/72；
    
- 新测试只能增加，不能修改旧断言以接受新行为；
    
- 新建软件 Change 继续使用 `matrix/change/v2`；
    
- full、hotfix、tweak 的返回值和阶段行为保持一致；
    
- 0.1.3 活跃 Change 可以继续恢复、Return、Abort 和 Archive；
    
- Archive 身份和固定摘要保持兼容；
    
- Prim、Arch 和原 Matt 安装逻辑保持稳定。
    

### matrix-find 功能

至少验证三种不同领域：

- 短视频制作；
    
- 生日聚会或活动筹办；
    
- 研究报告。
    

每个场景都必须证明：

- 能从自然语言澄清真实需求；
    
- 优先搜索完整工作流；
    
- 能生成领域专属阶段；
    
- 能发现能力缺口；
    
- 能搜索或创建能力；
    
- 能交付真实 Workflow Package；
    
- Agent 能通过生成入口推进工作流；
    
- 运行状态在项目中持久化；
    
- 能暂停、继续、退回和归档；
    
- 能局部替换某个步骤或 Skill；
    
- 多个工作流同时存在时能够正确选择；
    
- 不影响任何原 Matrix Change。
    

## 十一、推荐开发顺序

## 十二、最终产品关系

```
用户需求
   │
   ├─ 软件开发工作
   │    └─ 使用原 $matrix
   │         ├─ full
   │         ├─ hotfix
   │         └─ tweak
   │
   └─ 需要建立或寻找其他工作流
        └─ 使用 $matrix-find
             ├─ 澄清需求
             ├─ 搜索完整工作流
             ├─ 改造或生成
             ├─ 补齐 Skills
             ├─ 验证 Workflow Package
             └─ 安装新的业务工作流入口
                    └─ 后续由该工作流推进真实工作
```

## 立项结论

Matrix V0.2.0 的核心不是“让原 Matrix 五阶段适配所有工作”，而是：

> 在不改变 Matrix 0.1.3 软件工作流的前提下，新增一个能够理解需求、寻找工作流、组装能力并交付用户专属工作流的 matrix-find 系统。

原 Matrix 是稳定的软件工作流产品。

matrix-find 是新的工作流发现、生成和维护平台。

两者同属 Matrix 项目，但运行边界、状态数据和验收标准相互隔离。
