# Matrix V0.2.0 需求文档：通用自主工作流

> 本文档取代同名旧稿。旧稿描述的是 `$matrix-auto` 双轨方案与 Workflow Package 体系，该路线已废弃，去留见第十三节。本文依据《Matrix V0.2.0 自主能力优化与架构统一实施计划（修订版 v3）》《Matrix V0.2.0 实施计划评审结论》与《Matrix 自主能力优化需求说明》编写，只陈述需求与约束，不规定实施步骤。

## 一、一句话定义

Matrix V0.2.0 把 Matrix 从"软件开发五阶段工作流"演进为"单一 `$matrix` 入口的通用自主工作流"：

> 用户负责表达意图和期望；Agent 负责理解、探索、判断、执行和验证。目标明确时直接做完，目标模糊时先调查再定案；结果由 Runtime 实际执行的检查来证明，而不是由 Agent 自报通过。

原有五阶段工作流完整保留，称为 `classic`；新增的通用工作流称为 `auto`。两者共用同一入口、同一 Runtime、同一 `.matrix/`，不新增第二套任务管理或状态管理机制。

## 二、背景与目标

### 2.1 要解决的问题

用户并不总能把需求说清楚：可能只是觉得项目"用起来不舒服"、方案"不太合理"，或有一个目标却不知道从哪入手。现状的缺口：

- `$matrix` 默认把一切请求当作软件开发任务，没有"先理解这是什么"的环节；
- 澄清类能力（如 `grilling`）是散件，没有面向普通用户的通用协议把它们组织起来；
- 非开发任务没有执行与留痕体系；
- "完成"主要靠产物与 Agent 的断言，缺少由 Runtime 执行的客观检查，Agent 自证通过的问题没有解决；
- Matt Skills 的安装集合与完整性校验写死在流程里，通用任务被不必要的外部依赖约束。

### 2.2 目标：UAAP

UAAP（Universal Autonomous Agent Protocol，通用自主 Agent 工作理念）不是框架，也不是另一套工作流，而是对 Agent 应有工作方式的要求。V0.2.0 把它落为八项产品要求：

| 理念 | 产品要求 |
|---|---|
| 意图理解，而不是机械执行 | Agent 须还原用户想要的结果，不要求用户先写出完整需求 |
| 主动探索，而不是等待答案 | 能在仓库、文档、日志、Git 历史中查到的事实由 Agent 自己查 |
| 主动发现问题 | 不局限于用户指出的问题，须关注根因与相邻的重要隐患 |
| 独立判断 | 技术方案由 Agent 评估后自主定案，不罗列选项把决策责任交还用户 |
| 自主规划 | Agent 自行确定范围、顺序与验收标准，并按新证据调整 |
| 结果导向 | 以真正解决问题为准，原方案不合理时允许转向 |
| 自主探索与资源管理 | 探索与重试有预算，停滞时熔断而不是无限循环 |
| 持续验证 | 完成操作不等于成功，须按任务性质验证实际结果 |

### 2.3 通用性

能力不限于软件开发，同样适用于系统架构、网络安全、技术研究、产品设计、文档与数据分析、故障排查与运维、开放式探索等。Agent 按任务性质自选方法、工具与验证方式；不得把某一领域的固定流程或固定产物标题强加给所有任务。

## 三、产品边界

### 3.1 单一入口

- 所有开发与通用任务统一由 `$matrix` 承载。不设 `$matrix-auto`，不新建 `.scratch/auto`、`.matrix/auto/runs` 或 `.matrix/find`。
- Agent 每次请求都先执行 `inspect`，按其返回的 `default_workflow` 与 `autonomy_level` 路由；不得从聊天记录推断状态。
- 所有 Runtime 命令以 `node <matrix-skill-directory>/scripts/matrix-runtime.mjs <args>` 运行，使用项目自带的 Runtime。

### 3.2 两档工作流

| | `auto` | `classic` |
|---|---|---|
| 阶段 | `understand → execute → verify → close` | `full`：`open → design → build → verify → archive`；`hotfix`、`tweak`：`open → build → verify → archive` |
| 定位 | 通用自主工作流 | 原有证据驱动开发工作流 |
| 默认 | 全新 `matrix init` | 0.2.0 之前初始化的项目 |
| 安装的技能 | `matrix`、`matrix-status` | 全部十个 Matrix 技能 |
| Matt Skills | 可选；不要求，不做哈希校验 | Prim 下可选；Arch 下为冻结的 v1.3.1 能力集 |
| "完成"的依据 | Runtime 在 `run submit` 实跑检查，加上如实声明的评审来源 | 守卫条件、Contract 身份与审查回执 |

### 3.3 兼容性红线（classic 保持不变）

以下行为不得改变：`full`、`hotfix`、`tweak` 三个 profile；五个阶段及其守卫；Prim 与 Arch；`matrix/change/v2` 状态结构；Return、Abort、恢复、证据与两步归档机制；`--executor` 门禁；原有 CLI 命令的输出语义；历史 Change 与归档身份。V0.2.0 不把非开发任务塞进原五阶段，也不把原五阶段改造成通用 Profile。

### 3.4 不建 Run 的快速路径

纯问答、只读排查、单文件极小笔误修改不创建 Run，直接解答或执行，避免入口过触发。

## 四、auto 的核心行为

### 4.1 先查后问

提问之前必须先把能查的查完：仓库（代码、测试、`AGENTS.md`、`CLAUDE.md`、`GLOSSARY.md`、`docs/adr/`）、Matrix 状态与归档、日志与命令输出、Git 历史。只有查不到的事实才可以问用户。

### 4.2 模糊意图重构与自主定案

- 模糊请求须被重构为一个具体目标：Agent 自行调查、定位真正的问题（它可能不是用户报告的那个）、确定方向，并把目标、发现与决定写入 brief。
- 技术方案由 Agent 自主定案并说明理由，不得把选项清单交还用户。
- 只有三类情况可以打断用户：
  1. 实质性结果歧义：不同理解会导致目标、范围或验收项出现实质差异；
  2. 缺少外部私有信息：只有用户掌握、环境无法提供的事实；
  3. 不可逆或高危的对外动作：删除数据、改写 Git 历史、付款、对外发布、以用户身份发送消息。
- 需要专业资质的现实决定（法律、医疗、投资）不替用户做决定，只整理信息、选项与风险。

### 4.3 frame 的情境化确认

- `run frame` 冻结目标、验收项与检查命令，是自主执行的唯一起点。确认内容只有目标、验收项与检查，不含技术选项。
- 请求明确且有界：不带 `--wait`、`--require-confirmation`，Runtime 直接进入 `execute` 并返回摘要，由 Agent 向用户回显。
- 请求模糊、带探索性质或范围很大：Agent 先完成调查，再以 `--require-confirmation` 等待用户确认一次。
- 带 `--wait "<question>"`，或项目 `autonomy_level` 为 `strict` 时，一律进入 `await-user`。
- `execute` 开始后重新 frame 一律需要用户确认；修改目标或验收项不是内部决定。只调整实现方法用 `run pivot`，它会使本轮已有的检查结果与评审结论失效。

### 4.4 Runtime 实跑检查

- 检查命令在 `run frame` 声明并冻结。`run submit` 由 Runtime 在不持锁的情况下执行全部冻结命令，流式写日志，只记录退出码、耗时、超时与中断状态；失败直接回到 `execute`。
- Agent 不得自报检查通过。`run check` 只用于探索性诊断，不参与验收。
- 确实没有可执行检查的任务（调研、架构评估、产品分析等）须声明 `--no-checks-reason`；声明后 `.matrix/` 之外的代码仍有改动时，提交须给出警告。

### 4.5 诚实的评审来源声明

- `run verify` 必须覆盖全部验收项，并如实声明评审来源：`self`、`subagent` 或 `external`。三者都是声明而非可信证明，Runtime 原样记录并在 `verification.md` 中呈现，由用户自行权衡。
- 评审按 Standards 与 Spec 双轴分开进行，不得合并或跨轴排序。
- 不设无法验证的 `independent` 之类的标签。

### 4.6 预算与停滞熔断

- 每次提交无论成败都消耗预算：提交失败累计次数，上限默认 5。
- 验证失败回到 `execute` 并统计停滞：同一批未解决项连续 2 轮，或总轮次达 5 次，进入 `await-user`。
- 验收项为 `blocked` 时直接进入 `await-user`。
- 验证结果格式错误或 verifier 失败只累计尝试次数（上限 3），不计入停滞。
- 触顶后不得静默重试或自行重置；是否延展预算只能由用户通过 `run resolve` 决定。

### 4.7 单写者租约

- 一个工作区至多一个执行租约（`.matrix/current-run.json`），可以存在多个挂起的 Run。
- 所有变更命令必须针对持有租约的 Run，并携带 `--expect-revision`；不满足时拒绝执行。
- 从处于 `execute` 的 Run 切走、且工作区有 `.matrix/` 之外的未提交改动时，须给出警告。并行实施使用独立的 git worktree，不在同一工作区内同时推进两个 Run。
- Run 与 classic 变更共用同一事务闸门：任一方未完成的事务都会阻挡另一方的变更。

### 4.8 不自动续接（ambient resume 中立）

`inspect` 只呈现候选与状态。普通的新请求不得把用户卷入不相关的在途 Run 或 classic 变更；只有用户明确要求继续，或请求明显指向它时才续接。

### 4.9 缺少专有能力

缺少专有工具时，Agent 只能建议 `npx skills find <关键词>`，由用户决定是否安装；绝不无人值守地安装、升级或移除 Skill，主流程不自动运行 `find-skills`。

## 五、命令面与协议语义

以下为 0.2.0 的命令契约。所有 Runtime 命令以 `node <matrix-skill-directory>/scripts/matrix-runtime.mjs <args>` 运行。

- `inspect`：每次请求的首个调用。返回 `default_workflow`（`auto` 或 `classic`）与 `autonomy_level`（`balanced` 或 `strict`），以及当前 Run 或 classic 变更；没有任何在途项时返回 `NO_ACTIVE_CHANGE`。
- `run start (--request "<text>" | --request-file <path>) [--id <id>] [--title "<text>"] [--domain "<label>"]`：原样保存用户请求，创建 Run 并取得工作区租约。
- `run list`、`run select <run-id>`、`run select --none`：列出 Run、切换租约、释放租约。
- `run inspect [<run-id>]`：返回 Run 状态、确定性的 `continuation`、活跃与挂起列表。
- `run frame --goal "<text>" --accept "A1=<text>" [--accept "A2=<text>" ...] [--check "C1=<command>" ... | --no-checks-reason "<text>"] [--scope "<text>"] [--brief-file <path>] [--wait "<question>"] [--require-confirmation] --expect-revision <n>`：冻结目标、验收项与检查命令。
- `run resolve (--answer "<text>" | --answer-file <path>) [--confirmed] [--extend-budget <n>] --expect-revision <n>`：结束 `await-user`。
- `run pivot --reason "<text>" [--scope "<text>"] --expect-revision <n>`：只调整实现方法，不改目标与验收项；使本轮已有的检查结果与评审结论失效。
- `run check --cmd "<command>" [--timeout <ms>] --expect-revision <n>`：探索性诊断命令，不参与验收。
- `run submit --summary "<text>" [--timeout <ms>] --expect-revision <n>`：Runtime 在不持锁的情况下实跑全部冻结的检查命令，流式写日志，默认超时 120 秒。有失败则留在 `execute` 并累计提交失败次数；全部通过则进入 `verify`。
- `run verify --reviewer <self|subagent|external> (--result "A1=<passed|failed|blocked>[:<reason>]" ... | --result-file <path>) [--findings-file <path>] [--summary "<text>"] --expect-revision <n>`：必须覆盖全部验收项。全部 `passed` 进入 `close`；有 `failed` 回到 `execute` 并统计停滞；有 `blocked` 进入 `await-user`。
- `run close [--abort --reason "<text>"] --expect-revision <n>`：归档到 `.matrix/archive/runs/<run-id>/`，`verification.md` 由 Runtime 生成。
- 所有变更命令要求目标 Run 持有租约并携带 `--expect-revision <n>`；每个命令的输出都带 `continuation`，给出下一步的确切命令。
- `matrix skills audit <path-or-name>`：全局 CLI，只读静态扫描一个外部技能的冲突风险，不执行其脚本。

`inspect` 返回 `default_workflow: classic` 时，按 classic 兼容规程走原有流程。

## 六、安全门

- 自主性不越过系统权限、安全机制、数据保护要求与外部操作授权边界。`autonomy_level` 只有 `balanced` 与 `strict`，不提供可跳过安全门的取值。
- 第 4.2 节的三类打断边界与专业资质限制，在任何 `autonomy_level` 下都成立。
- 原则上不自动执行：批量删除、格式化、改写 Git 历史、付费、下单、对外发布、以用户身份发送消息。
- auto 取消 `--executor` 强制暂停；classic 维持原门禁。

## 七、持久化值与兼容规则

### 7.1 `.matrix/config.yaml`

- `default_workflow`：`auto` 或 `classic`，工作流的唯一权威来源。
- `autonomy_level`：`balanced` 或 `strict`。
- 可选预算：`max_iterations`（默认 5）、`max_stagnation`（默认 2）、`max_submit_failures`（默认 5）、`max_verifier_attempts`（默认 3）、`check_timeout_ms`（默认 120000）。
- 读取时剥离非引号内的 `#` 注释。该规则只用于 `config.yaml`，绝不用于 `matrix.yaml`，因为其标题可以合法地包含 `#`。
- 写入时清理死字段 `auto_transition`。

### 7.2 `default_workflow` 的解析与老项目缺省

- 读取顺序恒为：`config.yaml`（`default_workflow`）→ 对应 scope 的 `installation.json`（`workflow`）→ `classic`。
- 全新 `matrix init` 默认写入 `default_workflow: auto`；老项目升级后缺省按 `classic`，不静默切换。
- `matrix update` 以 `config.yaml` 的合法值为准，从不改变工作流；老项目缺 `default_workflow` 时，在结尾提示可运行 `matrix init --default-workflow auto` 切换。

### 7.3 `.matrix/installation.json`

- `workflow`：`auto` 或 `classic`。
- `orchestration.default` 恒为 `prim` 或 `arch`，与 `workflow` 是两个独立维度，`orchestration` 只对 classic 有意义。
- 技能集按 manifest 记录：`platforms.<id>.skills` 记录该平台实际安装的集合。`matrix update` 与 `matrix doctor` 的观测、备份与写回均以此为依据，不得把只装 2 个技能的 auto 项目"修复"回 10 个。
- 全新安装时，技能集合由 `workflow` 决定：`auto` 装 `matrix`、`matrix-status`，`classic` 装全部十个。

### 7.4 发布目录摘要

`releaseCatalog().digest` 始终基于全部 10 项技能源码计算，与项目实际选装 2 项或 10 项无关。auto 项目的 Runtime 入口不得因安装模式而失效。

### 7.5 Run 状态

- `.matrix/current-run.json`：`{ schema: "matrix/current-run/v1", run_id, updated_at }`，即单写者租约。
- `.matrix/runs/<id>/`：`state.json`、`events.jsonl`（追加式审计轨迹，随 Run 归档）、`brief.md`、`verification.md`（由 Runtime 生成，Agent 只读）、`logs/`（不入库的流式日志）。
- `state.json` 使用 `matrix/run/v1`，至少包含：`run_id`、`title`、`domain`（仅提示标签）、`phase`（`understand|execute|verify|close`）、`status`（`active|await-user|archived|aborted`）、`revision`、`iteration`、`submit_failures`、`verifier_attempt`、`raw_request`、`goal`、`scope`、`acceptance[]`、`required_checks[]`、`no_checks_reason`、`exploratory_checks[]`、`wait`、`budget`、`verification`（`reviewer`、`summary`、`findings[]` 与验证通过时记录的轻量变更指纹）、`created_at`、`updated_at`。
- 检查结果只记录命令、轮次、工作目录、状态、退出码、超时与中断标记、耗时、日志相对路径与截断标记；绝不把输出内容或预览写入 `state.json`。
- `domain` 不做七值枚举；没有机器读取方的字段不得进入 schema。
- Run 归档到 `.matrix/archive/runs/<run-id>/`，与 classic 的 `.matrix/archive/<change-id>/` 分属不同命名空间，互不干扰。

## 八、提交策略与防泄漏

- `.matrix/.gitignore` 以受管区块（`# BEGIN MATRIX MANAGED` / `# END MATRIX MANAGED`）幂等维护，安装与 `run start` 时同步；只追加受管条目，不覆盖用户自定义规则。
- 受管区块必须忽略：`active.json`、`current-run.json`、`installation.json`、`matt-installation.json`、`workflow.lock`、`transactions/`、`staging/`、`backups/`、`runs/*/logs/`、`archive/runs/*/logs/`、`changes/*/events.jsonl`、`changes/*/artifacts/handoff.md`。
- 原始命令输出只留在本机日志。入库的 `state.json` 与报告只含命令、退出码、耗时与日志相对路径。
- 检查命令不得携带字面凭据。Runtime 必须拒绝此类命令，而不是写入状态后再脱敏——脱敏后的命令无法在下一轮重新执行；凭据应从环境变量读取。
- 单条日志上限 512 KiB。超限后停止写盘并标记 `log_truncated`，继续排空子进程输出，不得因输出体积把检查判为失败。
- `raw_request` 与 `--answer` 原样保存并随 `state.json` 入库，因此 Agent 不得把凭据写入请求、目标、摘要等入库文本。
- 锁文件一旦被提交，换主机后 `doctor` 会拒绝修复，所以 `workflow.lock` 与 `transactions/` 必须被忽略；跨主机锁的诊断须明确指出可能是残留锁或误提交的锁，并给出核对指引。
- 受管区块必须有模板测试。

## 九、Matt Skills 与能力扩展

- auto 不做 27 项哈希锁死，不强制安装 Matt Skills，默认只向平台安装 `matrix` 与 `matrix-status` 两个技能；强模型可自由选用任何已安装的 Skill。
- Matt Skills 中值得保留的方法论（深模块与接缝、垂直切片防自证、Standards 与 Spec 双轴、基于 `git log` 热点的 YAGNI、先查事实再提问）蒸馏为 Matrix 自带的按需参考文档，附 MIT 出处声明。
- `classic + arch` 仍维持 ADR-0003、ADR-0004 的 v1.3.1 冻结契约，在途 arch 变更不受影响。
- auto 项目里，用户自行升级 Matt Skills 与在途 arch 变更互斥。
- `matrix update` 对 Matt 只读：只刷新 Matrix 资产并报告 Matt 兼容性，不追随上游新版本，不自行改写或移除 Matt 技能。auto 项目跳过 Matt 巡检提示；classic 项目保留 v1.3.1 修复提示。
- auto 下 `--with-mattpocock` 沿用现有的候选流程，只是不做运行时完整性锁。
- 以上决策以 ADR-0005 留痕，它部分取代 ADR-0003 与 ADR-0004。

## 十、Windows 边界

- 入口：路径包含 `#` 或 `%` 时不得静默失败；主模块判定使用 `pathToFileURL`，而不是字符串拼接的 file URL。
- 配置：三处读取 `config.yaml` 的解析器统一支持行内注释（见 7.1）。
- 子进程：超时后清理整棵进程树（Windows 用 `taskkill /PID <pid> /T /F`，Unix 杀进程组）并等待句柄释放；输出流式落盘，截断在捕获之后进行。
- 文件重命名：对 `EPERM`、`EBUSY`、`EACCES` 做有界重试（最多 5 次，30 至 100 毫秒退避）。
- 长文本走文件：请求、回答、brief、发现与结果使用对应的 `--*-file` 选项，避免命令行长度上限与引号改写。
- run-id：kebab-case 清洗，拒绝 Windows 保留名（`CON`、`PRN`、`AUX`、`NUL`、`COM1-9`、`LPT1-9`），同日重名追加 `-2`、`-3`。
- 检查命令与操作系统相关（例如 `NODE_ENV=test cmd` 在 Windows shell 下失败）；结果判定只依赖退出码。
- `engines.node` 为 `>= 22`（Node 18 与 20 均已停止维护）；CI 覆盖 Windows、Ubuntu、macOS 与 Node 22、24。

## 十一、测试契约变更的原则

- 基线 141 项测试中，133 项保持零改动通过。
- 仅 8 项断言因默认行为由 `classic` 改为 `auto` 而更新（涉及 `MATT_MISSING` 诊断、`--yes` 默认值、中文 `doctor` 输出、`update` 的 Matt 状态与修复提示、中文 `SKILL.md` 锚点句，以及 `SKILL.md` 中的 v2 命令字面量与 Prim、Arch 边界文案）。每处都在对应位置补回 `--default-workflow classic` 的等价回归用例，保证 classic 覆盖不丢失。
- 不得为了接受新行为而放宽清单之外的任何断言；全部 v2 流程测试保持零改动。"全部通过"的口径是"其余零改动"，不是"141 项原样通过"。
- `createDistribution()` 不传 `workflow` 时缺省仍为 `classic`，既有单测无需改动。
- 文档契约：四条 v2 return 与 abort 命令字面量必须存在于 `matrix/SKILL.md` 或其 `references/classic-compat.md`；`Prim`、`Arch`、`standalone`、`setup-matt-pocock-skills` 的边界文案在 `references/classic-compat.md` 中校验，中英文各一份。
- 新增测试须覆盖：预算封顶、大日志流式截断不杀进程、凭据不入状态、租约与脏工作区警告、重新 frame 后旧结论失效、verifier 尝试上限、指纹防篡改、Windows 入口与配置注释回归、v2 兼容、2 技能安装后 `update` 仍为 2 且 `matching`、打包安装离线跑通 Run 生命周期。
- 不引入模型在环的第二层评测（`matrix eval`）；确定性轨迹由 `node --test` 覆盖。

## 十二、明确不做

- `$matrix-auto` 双轨入口，以及 `.scratch/auto`、`.matrix/auto/runs`、`.matrix/find`。
- auto 下的 27 项哈希锁死与 Matt 强制安装。
- `src/eval.js` 第二层、`src/knowledge.js` 与 `~/.matrix/memory.json`。长期事实改为在收尾时按仓库既有惯例沉淀到 `AGENTS.md`、`CLAUDE.md`、`GLOSSARY.md` 或 `docs/adr/`。
- `skills attach`、`skills detach`、`skills list` 与 `.matrix/capabilities.json`；只保留只读的 `matrix skills audit`。
- `domain` 七值枚举，以及没有机器读取方的 schema 字段。
- `hook-guard` 推迟至 0.2.x：阶段写拦截在不同宿主上保证不一致，容易误锁编辑器。防线统一收口到三个宿主行为完全一致的 Runtime `submit` 与状态校验。
- 可越过安全门的 `full-auto` 自治级别。
- 未经确认安装 Skill；静默执行外部写入、发布、付款或消息发送；仅凭对话声明任务完成。

## 十三、延期：Workflow Package 与 find-skills 自动拼装

旧稿把"找、改、生成可复用工作流并交付为 Workflow Package"列为 `matrix-find` 收编后的 M3 至 M5 路线。V0.2.0 明确不做，理由：

- 0.2.0 的目标是先证明单一入口的自主闭环成立：理解、执行、Runtime 实跑检查、诚实验证。可复用工作流平台建立在这个闭环之上，顺序不能颠倒。
- 该路线需要一整套尚未设计的机制：安装确认、精确提交 SHA 与内容哈希、回滚、步骤级与 Skill 级替换、跨领域验收。在自主闭环未经真实使用检验之前投入，属于为尚不存在的需求做设计。
- 主流程不自动运行 `find-skills`、不静默安装第三方 Skill 的原则不变；缺少专有能力时只提示 `npx skills find`。

重新评估的条件：用户反复需要把某类任务固化为可复用工作流。届时在该闭环的实证基础上另行立项，而不是在 0.2.0 内预留目录或 schema。

## 十四、验收标准

### 14.1 自动化

- `node --test` 全量通过，`npm run pack:check` 通过；变更范围符合第十一节。
- CI 在 Windows、Ubuntu、macOS 与 Node 22、24 上全绿。

### 14.2 安装与升级

- `matrix init <dir> --yes` 默认得到 `auto`、`balanced` 与两个技能；`.matrix/.gitignore` 受管条目完整。
- `matrix update --skip-self-update` 之后，auto 项目仍为两个技能且状态为 `matching`，不被补装回十个。
- 老项目 `matrix update` 之后 `default_workflow` 仍按 `classic` 解析，并提示可用 `matrix init --default-workflow auto` 切换；在途 v2 变更可以继续 Return、Abort 与 Archive。
- `matrix init --default-workflow classic` 与 `--autonomy strict` 按参数生效。

### 14.3 行为

- Agent 无法自报通过：`run submit` 的检查由 Runtime 执行，`run check` 不参与验收。
- 一条模糊诉求可以走通 `run start → frame → execute → submit → verify → close` 全闭环；框定前 Agent 先完成调查，确认只涉及目标、验收项与检查。
- 提交连续失败 5 次、同一批未解决项连续 2 轮或累计 5 轮、verifier 连续 3 次无有效结果时，Run 进入 `await-user` 而不是继续循环。
- 不持有租约或 `--expect-revision` 不匹配时，变更命令被拒绝。
- 普通新请求不会续接不相关的在途 Run 或 classic 变更。
- 四份双语参考文档内容一一对应；`classic-compat.md` 的中英文版本均逐字包含四条 v2 命令字面量与 `Prim`、`Arch`、`standalone`、`setup-matt-pocock-skills`。

### 14.4 真实环境

- 在当前环境（`.agents/skills`）用真实模型实测一条模糊诉求的完整闭环。
- ZCode 与 Claude Code 的端到端真实会话验收，由用户在交付后各完成一次，并明确记为手动验收项，不以自动化测试代替。
