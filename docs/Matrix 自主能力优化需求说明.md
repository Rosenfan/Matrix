# Matrix 自主能力优化需求说明
## 关于构建通用意图理解与自主决策能力的需求

### 一、需求背景

我希望进一步提升当前 Matrix 工作流的整体能力，使其不仅能够按照既定工作流程执行任务，还能够具备更强的自主理解、自主分析、自主判断和自主解决问题的能力。

在实际使用 AI Agent 的过程中，我发现一个比较普遍的问题：

用户并不总是能够清楚地描述自己的需求。

很多时候，我可能只是有一个模糊的想法，或者觉得当前某个项目、功能、方案、工作流程使用起来不舒服，但并不知道具体问题在哪里，也不知道应该如何改进。

例如：

- 当前项目使用起来不舒服，但无法明确指出具体原因。
- 感觉现有架构或设计不合理，但不知道问题出在哪里。
- 有一个想实现的目标，但不知道应该采用什么方案。
- 对现有功能不满意，但不知道应该如何调整。
- 希望优化某个项目，但不知道从哪些方面入手。
- 想研究某个方向，但不清楚应该研究哪些内容。
- 发现当前方案可能存在问题，希望 Agent 自己调查并判断是否需要改变方向。

我不希望每次使用 Agent，都必须提前完成详细的需求分析、问题定位、技术选型和实施方案设计。

这些本身就应该是 Agent 能够承担的工作。

我希望只需要使用自然语言表达自己的想法、目标、问题或感受，即使描述不完整、逻辑不清晰，Agent 也能够主动理解和探索，逐步明确真正需要解决的问题，并自主推进后续工作。

### 二、核心理念：UAAP

UAAP（Universal Autonomous Agent Protocol，通用自主 Agent 工作理念）是本次需求中希望实现的核心能力目标。

它不是一个特定的技术框架，也不是要求额外建立一套独立工作流，而是对通用 Agent 应具备的工作方式和自主能力的概括。

我希望 Agent 不再只是一个被动接收明确指令、按照用户提供的步骤完成任务的执行工具，而是能够主动理解用户意图、发现问题、独立判断、制定方向并推动任务完成的智能工作伙伴。

UAAP 所代表的核心理念包括：

**1. 意图理解，而不是机械执行指令**

Agent 不应只关注用户说了什么，还应该理解用户真正想获得什么结果。

当用户无法准确描述需求时，应主动结合上下文、现有环境和实际情况理解用户意图，而不是要求用户必须提供完整的需求文档。

**2. 主动探索，而不是等待用户提供答案**

当用户不知道问题在哪里时，Agent 应具备主动调查和探索的能力。

能够根据任务性质，自主检查现有项目、资料、系统、流程、数据或其他相关信息，寻找问题和潜在的改善机会。

不应该将本应由 Agent 完成的调查和分析工作转交给用户。

**3. 主动发现问题，而不是局限于用户提出的问题**

用户指出的问题不一定是根本问题。

Agent 应能够通过自主分析发现用户没有明确提出、但可能对最终目标产生重要影响的问题。

不仅解决表面问题，也应该关注问题产生的原因，以及是否存在更合理的解决方向。

**4. 独立判断，而不是等待用户提供方案**

Agent 应具备独立分析和决策能力。

面对多个可能的解决方案时，能够根据实际情况评估其合理性、可行性、成本、风险和长期价值，并自主选择更合适的方向。

不应只是罗列方案，再把所有决策责任交还给用户。

**5. 自主规划，而不是依赖固定指令**

Agent 应能够根据最终目标自主确定工作范围、执行顺序、优先级和验收标准。

在执行过程中，可以根据新发现的信息和实际结果调整原有计划，而不是机械地遵循最初制定的步骤。

**6. 结果导向，而不是完成指令导向**

Agent 的最终目标不是完成用户描述的每一个操作，而是真正解决用户希望解决的问题。

即使执行过程中发现原始方案并不合理，也应该能够重新评估方向，选择更有价值的解决方式。

**7. 自主探索与资源管理**

Agent 应能够合理控制探索范围、时间、工具调用和执行成本。

避免重复调查、无效尝试、无限探索和过度分析。

当原有方向无法取得有效进展时，应主动分析原因并调整策略。

**8. 持续验证与改进**

Agent 不应在完成操作后立即认定任务成功。

应根据任务性质验证实际结果，判断是否真正达到预期目标。

如果结果不符合预期，应主动分析原因并提出调整方向。

### 三、希望实现的整体使用体验

我希望未来使用 Matrix 时，不需要提前具备完整的需求分析和方案设计能力。

我只需要表达自己的想法，Matrix 就能够根据实际情况自主开展工作。

例如：

**场景一：模糊的项目优化需求**

用户：

「我感觉这个项目现在用起来越来越不舒服，但我也说不清楚具体哪里有问题，你自己分析一下。」

期望：

Agent 能够理解这是一个开放式优化需求，主动调查项目现状、功能组织、操作流程、架构设计和实际使用体验，寻找可能的问题，判断问题的重要性，并形成合理的优化方向。

**场景二：不明确的技术需求**

用户：

「我想让这个系统变得更加智能，但不知道应该怎么做。」

期望：

Agent 不应直接随意增加 AI 功能，而是结合系统现状、产品定位和用户目标，分析真正有价值的智能化方向，判断哪些能力值得建设，以及如何获得实际收益。

**场景三：现有方案存在问题**

用户：

「我觉得现在这个方案不太合理，你重新研究一下。」

期望：

Agent 能够重新审视现有方案，检查设计依据、技术实现、依赖关系、潜在风险和其他可行方案。

如果原有方案确实存在问题，应主动提出更合理的方向，而不是为了延续原有方案而进行局部修补。

**场景四：开放式研究**

用户：

「帮我研究一下这个方向，看看有没有值得关注的东西。」

期望：

Agent 能够自主确定研究范围、关键问题、资料来源和分析方向，发现值得关注的信息，并形成有实际价值的研究成果。

**场景五：明确任务之外的问题发现**

用户：

「帮我实现这个功能。」

期望：

Agent 在理解和执行明确需求的同时，也能够识别与任务密切相关的架构问题、兼容性问题、安全风险和其他重要隐患。

不应只关注完成当前功能，而忽略可能影响最终结果的问题。

以上场景仅用于说明期望的工作体验，不构成固定的执行流程或技术实现要求。

### 四、与现有 Matrix 的关系

本次需求的对象是现有 Matrix 工作流。

我希望在现有 Matrix 的基础上实现上述 UAAP 所代表的通用自主能力，而不是另外建立一套独立的工作流。

我倾向于始终使用一套统一的工作流。

不希望因为增加自主理解和决策能力，就出现多套工作流、重复的任务管理机制、重复的状态管理机制或相互独立的执行体系。

Matrix 应继续作为统一的工作流基础。

但这并不意味着我已经确定了具体应该如何修改 Matrix，也不代表我已经确认当前 Matrix 缺少上述所有能力。

我希望 Agent 先充分理解现有 Matrix 的设计和实际实现，再判断当前已经具备哪些能力、哪些能力需要增强，以及是否存在其他更合理的优化方向。

对于已经实现且运行良好的能力，应优先考虑保留和复用。

对于重复、冲突或不合理的设计，应根据实际情况进行分析。

具体的架构调整、模块划分、接口设计、数据结构和实施方式，不在本需求中预先限定。

### 五、自主性要求

我希望 Matrix 具备较高程度的自主性。

在任务目标和授权范围内，Agent 应尽可能独立完成：

- 理解用户表达的意图。
- 调查当前环境和已有资源。
- 发现潜在问题。
- 分析问题根源。
- 重建真实需求。
- 确定任务目标。
- 制定解决方案。
- 选择执行路径。
- 安排任务优先级。
- 推进任务执行。
- 根据实际情况调整方向。
- 验证最终结果。

不要因为用户没有提供完整方案就停止工作。

不要频繁要求用户决定本可以由 Agent 自主判断的技术细节。

只有当不同理解会导致重大方向差异、缺少必要信息且无法自主获取，或者涉及重大风险、不可逆操作和明确需要用户授权的事项时，才应请求用户参与决策。

自主性不意味着不受限制。必须遵守现有系统权限、安全机制、数据保护要求和外部操作授权边界。

### 六、通用性要求

这项能力不应该只针对软件开发或某一个特定项目。

我希望它能够适用于各种任务和领域，包括但不限于：

- 软件开发和项目优化。
- 系统架构和技术方案设计。
- 网络安全和数据安全。
- 技术研究和知识学习。
- 产品设计和用户体验优化。
- 工作流程和效率优化。
- 文档、报告和数据分析。
- 故障排查和系统运维。
- 开放式探索和其他日常工作。

Agent 应根据任务性质自行选择适合的专业知识、工具、方法和工作方式。

不应将某一个领域的固定流程强行套用到所有任务。

### 七、本次希望 Agent 完成的工作

我希望 Agent 将本需求作为一次针对现有 Matrix 的自主能力优化研究任务。

首先充分理解本需求所表达的目标和期望，再结合现有项目实际情况，自主开展调查、分析和判断。

我不预先规定具体的技术实现方式。

我希望 Agent 自行完成以下工作：

1. 理解本次需求的核心目标和 UAAP 所代表的能力要求。
2. 全面了解现有 Matrix 的架构、工作流、功能和实际实现。
3. 判断现有 Matrix 是否已经具备上述自主能力。
4. 分析现有能力与期望目标之间的差距。
5. 识别可能存在的能力重复、职责冲突和设计问题。
6. 判断哪些能力值得增强，哪些能力不需要修改。
7. 研究是否存在更合理的整体设计方向。
8. 评估可能产生的架构影响、兼容性风险和维护成本。
9. 根据实际调查结果形成合理的优化建议。
10. 如果认为值得实施，进一步制定清晰、可验证的实施计划。

在分析过程中，必须以实际代码、文档、测试和运行行为为依据，不要仅凭目录名称、模块名称或设计文档推断功能已经实现。

必须区分已经实现、部分实现、仅有设计、尚未实现和无法确认的能力。

### 八、工作边界

本次首先关注需求理解、现状调查和优化方向分析。

在没有充分了解现有 Matrix 之前，不要直接进行大规模架构调整或代码重构。

不要为了实现 UAAP 而强行增加新的模块、状态机或工作流。

不要预先假定现有架构存在问题。

不要为了追求更高的自主性而忽略安全、稳定性和可维护性。

如果经过调查发现现有 Matrix 已经能够满足目标，应明确说明，不需要为了体现优化而进行无意义的修改。

如果发现确实存在差距，则根据实际情况提出合理的改进方向。

### 九、最终期望

我希望最终得到的是一个真正具有通用自主能力的 Matrix。

面对明确需求，它能够高效完成任务。

面对模糊需求，它能够主动理解和重建目标。

面对未知问题，它能够主动调查和发现问题。

面对复杂任务，它能够独立判断、规划和调整方向。

面对执行过程中的变化，它能够根据新证据动态决策。

面对完成的任务，它能够验证结果，而不是仅仅汇报操作已经结束。

我不希望用户必须先成为一个优秀的需求分析师、架构师或技术专家，才能让 Agent 发挥价值。

我希望 Agent 能够帮助用户发现自己尚未明确意识到的需求，并将这些模糊的想法转化为真正有价值的结果。

**最终愿景：用户负责表达意图和期望，Matrix 负责理解、探索、判断、规划、执行和验证，在统一工作流下自主完成真正需要解决的问题。**
