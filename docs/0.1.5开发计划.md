# Matrix V0.1.5 开发计划

定位：0.1.4（Matt Skills 深度融合）之后的**链路修复版本**——只做两项基础设施修复：`.claude/skills` 平台解耦（F5）与安装/校验链路 EOL 归一化（F6），为 0.1.6（体验与协作特性）铺平地基。原计划中的 F1–F3、F7–F9 已移至 0.1.6，见《0.1.6开发计划.md》。

- 分支：`codex/matrix0.1.5`（自 master `35b50ac` 切出）
- 基线：v0.1.4，测试 116/116 通过（2026-09-19 于 `7f50309` 复测）

## 一、需求与差距

| 需求 | 现状 | 归属 |
|---|---|---|
| 去除 `.claude/skills` 平台硬依赖（2026-09-19 排查确认） | catalog/self-update/测试/Python 暂存均硬编码该路径 | F5（0.1.5） |

| init/update 拉取最新 mattpocock/skills | 固定受支持 release | 归入 0.2.0（见第四节） |

## 二、特性设计

### F5 — `.claude/skills` 平台解耦（skills 源平台无关化）

背景（2026-09-19 实测，提交 52f1575 → 5bd6d92）：`.claude/skills` 只是 Claude Code 环境的安装产物目录，但当前产品把它当硬依赖——`src/catalog.js` 以它为英文 skills 源、`src/self-update.js:42` 候选包硬校验、`test/package.test.js` 直接读取、Python 兼容 runtime 从它暂存。删除该目录即导致 `npm test` 全挂、init/update 不可用、自更新拒绝；换一个没有 `.claude` 目录的 agent 环境（如纯 Codex）项目即瘫痪，属平台耦合缺陷。

方向：

- skills 源迁至平台无关位置（建议 `assets/skills/`，与 `assets/skills-zh-CN/` 同层），`releaseCatalog()` / `sourceSkillsRoot()` 改指向新位置；
- `.claude/skills` 降级为 claude-code 平台的**安装目标**（与 codex 的 `.agents/skills` 对等），不再承担"源"职责；
- `self-update.js` 候选包校验改校验新源位置；`package.json` `files` 白名单同步调整；
- 迁移兼容：已安装项目（installation.json v3）升级到新版时由 `update` 按 v4 清单一次性刷新。

### F6 — 安装/校验链路 EOL 归一化

背景（2026-09-19 实测）：`hashDirectory` 按原始字节哈希。同一份 0.1.4 内容，git 仓库检出（`core.autocrlf=true` 统一 CRLF）与 npm 发布包（打包时工作树的混合 EOL）字节不同、逻辑内容一致，导致仓库 CLI 与 npm 安装的 CLI 对同一项目各自重算的 catalog 指纹**永远不一致**——`PROJECT_RUNTIME_RELEASE_MISMATCH` 在两个官方内容源之间必然出现，用户侧表现为"明明是最新版却报不匹配"。

方向（组合）：

- `hashDirectory` 对文本内容先做 EOL 归一化（CRLF/CR → LF）再计算；`installation.json` 清单版本 v3 → v4，升级后首次 `update` 重新登记；
- 仓库新增 `.gitattributes` 规范交付物 EOL（`* text=auto` + `src/`、`assets/`、`.claude/skills/` 等交付目录 `eol=lf`），发布打包从干净提交执行；
- 效果：仓库检出、npm 包、本地 tgz 三种来源只要逻辑内容一致即互相认可，doctor 不再因换行符误报。

## 三、修改范围、风险与验证

| 文件 | 改动 |
|---|---|
| `src/catalog.js` | F5 skills 源位置迁移；F6 `hashDirectory` EOL 归一化 |
| `src/self-update.js` | F5 候选包校验改新源位置 |
| `package.json` | F5 `files` 白名单调整（`.claude/skills/*` → `assets/skills/*`） |
| `.gitattributes`（新） | F6 交付物 EOL 规范 |
| `test/` | F5/F6 对应调整 `package.test.js` 等路径断言 |

不触碰：`workflow.js`、`workflow-transaction.js`、`distribution.js` 核心计划与提交逻辑、Matt 兼容性合同——0.1.3/0.1.4 兼容性红线不受影响（仅改变源的存放位置与哈希口径，不改安装事务语义）。

风险：

- **F5 属结构性迁移**：skills 源位置变更涉及 `files` 白名单、self-update 校验与既有测试路径，需一次性同步到位；旧项目 installation.json（v3）由 `update` 升级为 v4 并全量刷新，不引入双源并存期。
- **F6 改哈希口径的过渡**：清单 v3 → v4 后，既有安装会被一次性判定为 outdated 并由 `update` 刷新（出现一次"重新安装"属预期）；归一化只影响哈希，不改变落盘文件内容。

验证：

1. 基线：现有 116 测试全绿；新增/调整测试全部通过。
2. F5：在无 `.claude` 目录的干净环境（纯 Codex）跑 init/update 全链路成功；`npm run pack:check` 确认新源位置入包、旧路径无泄漏。
3. F6：同一提交分别以仓库检出与 `npm pack` 产物运行 doctor，两者对同一项目均判定 healthy；构造 CRLF/LF 混合样本验证哈希稳定。
4. 收尾：`npm run pack:check` 打包清单无泄漏；发布 `release: v0.1.5`。

实施顺序：F6（EOL 归一化哈希 + `.gitattributes`，小而独立，先消除环境误报）→ F5（skills 源迁移）→ 测试补齐 → README → `release: v0.1.5`。

## 四、边界澄清：拉取最新 Matt skills（归入 0.2.0）

「拉取最新」在 0.1.5/0.1.6 的语义 = **重新拉取当前受支持的 release（v1.2.3）**。原因：内容校验依赖按发布预置的 Hash 表，任意新上游内容在没有新版 Matrix 的情况下无法验证——这是兼容性合同（CONTEXT.md「Matt compatibility contract」，明确避免 floating latest）的约束。

真正的「联网解析最新稳定版 → 兼容性检查 → 精确 SHA 安装」已在《0.2.0需求文档》第八节定义，涉及合同版本化（ADR 0003）与信任模型调整，归入 0.2.0。本两版均不实现。

## 五、版本路线（0.1.5 → 0.1.6）

两个版本**串行开发**，不同时开两条开发分支，避免交叉污染。

### 分支流

```
master(35b50ac)
  └─ codex/matrix0.1.5   ← 当前，完成 F6 → F5 → release: v0.1.5
       └─ 合回 master（ff-only）+ tag v0.1.5 + 删除开发分支
            └─ codex/matrix0.1.6   ← 自 0.1.5 发布点切出，完成 F1-F3、F7-F9 → release: v0.1.6
                 └─ 合回 master（ff-only）+ tag v0.1.6 + 删除开发分支
```

### 发布流（每版相同）

1. 开发分支上测试全绿后，`package.json` version bump，同步 `matt-catalog.mjs` 的 `matrixVersion` 字段（沿用 0.1.4 惯例；注意该字段参与 catalogDigest，bump 后已安装项目首次 update 会触发一次 Matt 重新核对，属预期）。
2. 提交 `release: v0.1.x`，确认 `git status` 干净。
3. `git checkout master && git merge --ff-only codex/matrix0.1.x && git tag v0.1.x`。
4. `git push origin master --tags`，随后 `npm publish`（`prepublishOnly` 自动执行 test + pack:check；注意发布时的浏览器 OIDC 认证只能在交互终端完成，非交互 shell 会失败）。
5. 创建 GitHub Release：`gh release create vX.Y.Z --title "Matrix vX.Y.Z" --notes-file <说明文件> --latest`（中文说明，沿用既有风格：摘要 + 主要更新 + 升级 + 验证；0.1.5/0.1.6 两个 tag 的 release 已于 2026-09-19 补建）。
6. 发布验证：`npm view @rosenfan/matrix version` 与本地 tag 一致；GitHub 仓库内容与本地 master 一致；Releases 页出现对应条目。
7. `git branch -d codex/matrix0.1.x` 清理开发分支。

### 兜底

- **推送会公开累积文档**：发布 0.1.5 推 master 时，会连带公开 0.2.0需求文档、两版开发计划等尚未推送的提交（属预期）；若有不想公开的内容，发布前提出。
- **npm 发布失败**：不影响已推送的 git 状态；修复后直接重试 publish，git 不需回滚。
- **发布后发现缺陷**：从对应 tag 切 `hotfix/v0.1.x.y` 分支修复并 patch 发布；若缺陷同时影响下一版开发分支，cherry-pick 修复提交过去，不整体合并。
- **发布纪律**（沿用既有结论）：推 GitHub 只含项目本体，本地 skills/工具目录永远 gitignore；发布打包必须从干净提交执行，禁止本地 tgz 测试构建混入发布链路。
