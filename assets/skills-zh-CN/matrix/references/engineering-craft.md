# 工程准则

从 Matt Pocock 的 skills 中提炼的五项做法，为改动代码库的 `auto` Run 重新表述。它们是判断依据，不是关卡：没有任何一项会暂停 Run 或要求仪式。何时适用由 Agent 判断，并把判断记进 brief。

## 1. 深模块，以及以接缝作为测试边界

- 小接口后面藏大量行为，模块才算深。深浅在接口处衡量——调用方或测试每学一单位接口能做多少事——绝不用实现行数与接口行数之比来衡量。
- 接口是调用方必须知道的全部：参数与结果，以及顺序规则、不变量、失败方式和必需的配置。
- 接缝（seam）是不必在那处改代码就能替换行为的位置，也就是接口所在之处。接缝放在哪里本身就是一个设计决定，与它背后藏什么无关。
- 调用方与测试跨过的是同一道接缝。测试若越过接口——私有方法、内部协作对象、绕开接口直接查数据库之类的旁路——说明模块形状不对。能在内部重构后原样存活的测试，才是接缝放对了的证明。
- 依赖由外部传入而不是自己构造；返回结果而不是修改共享状态。两者都能缩小测试需要准备的东西。
- 只有当确实有东西在两侧变化时接缝才成立：只有一个适配器只是假想的接缝，两个（例如生产实现与内存替身）才值得引入。不要仅仅因为测试要用，就把内部接缝暴露到公开接口上。
- 删除测试：设想把这个模块删掉。复杂度随之消失，它只是透传；复杂度在每个调用方重新出现，它才有存在价值。
- 加深模块之前先给它的依赖分类：进程内（合并后直接测）、本地可替换（用替身测）、远程但自有（一个端口配真实与内存两种适配器）、真正的外部（一个端口配测试中的 mock）。
- 接口形状本身不确定时，勾勒两三个刻意不同的接口——入口最少、最灵活、对最常见调用方最省事——就深浅、变化集中在哪里、接缝位置逐一比较。由 Agent 选定一个并记录理由。
- 替换，而不是叠加：加深后的接口上有了测试，就删掉原先针对被吸收的浅模块的单元测试。

## 2. 垂直切片，以及不会自证的测试

- 一次推进一个垂直切片：一个失败的测试，让它通过的最小实现，如此重复。每个循环都是一颗示踪弹，指出下一个切片该是什么。
- 不要水平切片——先写完全部测试，再写全部实现。成批的测试验证的是想象中的行为，并在理解实现之前就把结构定死。
- 先红后绿。先看到测试因预期原因失败，再写让它通过的代码。
- 无法与代码产生分歧的测试什么也证明不了。以下三种写法会不知不觉写出这种测试：
  - 同义反复的期望值：期望值按实现的算法重新算了一遍。期望值要来自独立的来源——已知的字面量、手算的例子、规格说明。
  - 与实现耦合：断言内部协作对象的调用次数或顺序，或测试名描述的是"怎么做"而不是"做什么"。
  - 旁路观察：不在接口上、而在别处检查结果。
- 用仓库的领域语言（`GLOSSARY.md`、ADR）按可观察的行为给测试命名："用户可以用有效购物车结账"，而不是"checkout 调用 payment service"。
- 只在你无法控制的边界上使用 mock——第三方 API、时间、随机数，有时包括文件系统或数据库。绝不 mock 自己的模块。
- 重构不属于红绿循环。把它放到评审阶段提出。

## 3. 在两条独立的轴上评审

- Standards 轴问的是改动是否遵循本仓库成文的编码方式。读那些写明规范的文档（`CONTRIBUTING.md`、`AGENTS.md`、lint 配置）。什么都没写时，退回到一份固定的代码坏味道基线：神秘命名、重复代码、依恋情结、数据泥团、基本类型偏执、重复的 switch、霰弹式修改、发散式变化、投机性通用（speculative generality）、过长的消息链、中间人、被拒绝的遗赠。
- 两条规则约束这份基线：仓库成文的规范永远优先于它；每一条坏味道都只是带标签的判断（"可能是依恋情结"），绝不是违规。工具已经强制的事项直接跳过。
- Spec 轴问的是改动是否做到了被要求的事。在 `auto` 中，规格就是 Run 冻结的 `goal`、`scope` 与 `acceptance[]`。报告缺失或只做了一部分的需求、没人要求的行为，以及看起来实现了但其实不对的需求。每条发现都引用对应的验收 id。
- 两份报告分开保留。代码可能通过一条轴而不通过另一条；合并或跨轴重新排序会让较强的那条轴掩盖较弱的。每条轴各给出自己的条数与最严重的发现，不要评出一个总赢家。
- 先钉住比较范围（`git diff <fixed-point>...HEAD`），确认 diff 非空，再开始评审。
- 每条轴在干净的上下文里读得更准。宿主提供子 Agent 时，把两条轴放进不同的子 Agent，并在 `run verify` 中声明 `--reviewer subagent`。

## 4. YAGNI：把范围收敛到真正在变的地方

- 重构只有在未来改动会落地的地方才有回报。扫描设计改进之前先决定看哪里：用户指明了方向就照做；否则走一遍 `git log --oneline`，让反复出现的路径——热点——先把注意力拉过去。只有历史里看不出明显热点时才扩大扫描范围。
- 先读 `GLOSSARY.md` 与覆盖该区域的 ADR。不要重新争论已记录的决定，除非摩擦确实大到值得重开，而且要明确说出来。
- 值得找的摩擦：理解一个概念要在许多小模块之间来回跳；接口几乎和实现一样复杂；只是为了可测试才抽出的纯函数，而真正的 bug 藏在它们的调用方式里；模块越过接缝相互泄漏；没有测试、或经由现有接口无法测试的代码。
- 删掉投机性通用：为规格中并不存在的需求而加的抽象、参数与钩子。
- 给候选排序并推荐一个。给出有理由的明确判断，而不是一份菜单；不同方案的元素确实能互补时，混合方案也可以。
- 每一条收益都说具体：哪个接口变小了，变化与 bug 汇聚到了哪里，哪些测试可以删掉。

## 5. 先调查，只在决策前沿提问

- 把工作看成一棵决策树：每个决定都挂在它上面的决定之下。前沿是所有前提已经落定的决定。
- 查事实是 Agent 的工作。凡是查得到的东西——文件系统、可用工具、Git 历史、日志、配置——都自己查，绝不问用户。
- 仍在调查中的事实就是一个未落定的前提：只有位于它下游的问题需要等待；前沿的其余部分照常推进。
- 到达用户那里的只有决定，而且只能是必须由用户拥有的那些（见 `uaap-protocol.md` 的打断边界）。技术决定由 Agent 做出并记录。确实该由用户决定的事，提问时附上你推荐的答案。
- 每个分支都已被证据落定、由 Agent 决定、或交给用户之后，探索才算完成——没有任何东西被默默假设。

## 在 Run 中的用法

- 理解：先调查（5）；请求属于架构或重构类任务时，框定之前先收敛到热点（4）。
- 框定：验收项描述接缝处的可观察行为（1、2）；检查命令就是把这些行为跑起来的命令。
- 执行：按垂直切片推进（2）；凡是新建接口的地方，运用深模块的思路（1）。
- 验证：在两条轴上评审（3），并按 `domain-verification.md` 的要求如实声明评审者。
