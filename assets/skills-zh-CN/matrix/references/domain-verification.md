# 分领域验证

按任务性质选择证据，不要把某一个领域的证明方式硬套到另一个领域。Runtime 只依据冻结的 `acceptance[]` 与 `required_checks[]` 判定 Run 的结果；声明的评审者永远不是可信证明。本文件定义每类任务的诚实证据长什么样。命令以 `node <matrix-skill-directory>/scripts/matrix-runtime.mjs <args>` 运行。

## 按任务类型选择证据

| 任务类型 | Runtime 执行什么 | Agent 必须附上什么 |
|---|---|---|
| 代码改动 | `run submit` 时执行每一条冻结的 `--check` 命令 | `failed` 的原因，写明检查 id 与失败的行为 |
| 调研、架构审视、安全评估、产品分析 | 不执行（`--no-checks-reason`） | 事实溯源：每条结论都绑定到带行号的文件路径、某条命令及其输出，或具名的外部来源 |
| 运维（配置、迁移、部署、数据修复） | 一条对结果状态只读的探测命令 | 变更前后的状态、实际运行的命令，以及刻意未动的部分 |

混合了多种类型的 Run，为其可执行的部分声明检查命令，其余部分提供事实溯源。

## 代码改动

- 在 `run frame --check "C1=<command>"` 中声明检查。`run submit` 在不持锁的情况下亲自执行全部检查，把输出流式写入 `.matrix/runs/<run-id>/logs/`，默认超时 120 秒。记录下来的退出状态是唯一被接受的结果；绝不自行把某项检查标为通过。Runtime 会拒绝携带字面凭据的检查命令。
- `run check --cmd "<command>"` 用于探索，永远不能满足验收项。
- 优先选择以退出码为裁定的命令：仓库的测试命令、lint 或类型检查、构建、聚焦的脚本。一条命令可以支撑多个验收项。
- 提交通过后，在 verify 摘要里写明对应关系："A1 passed — C1 `node --test` exit 0"。
- 提交通过到 `run close` 之间不要改动实现：Runtime 在 `run verify` 时把工作区与已提交的状态比较，在 `run close` 时与已验证的状态比较，不一致就把 Run 退回 `execute`。

## 调研与分析类交付物

- 每条论断都带来源：`src/workflow.js:1103`、某条命令及它打印的行，或一份外部文档及其 URL 与查阅日期。没有来源的论断只是假设，要按假设标注。
- 优先使用一手来源：代码与测试优先于设计文档，留下的运行记录优先于回忆，标准或厂商文档优先于二手综述。
- 在交付物中把三类内容分开：已验证、推断得出、未检查。"未验证"是正当的发现，与之对应的 verify 结果是 `blocked`。
- 把你依赖的事实用 `run check` 留档（一次 `git log`、一次 grep 计数、一段脚本输出），使其有据可查。

## 运维

- 用评审者可以复跑的命令证明结果状态：`curl -fsS <health-url>`、一条计数查询、工具的 dry run。变更命令本身退出码为零不构成证明。
- 记录变更前后的状态、究竟改了什么，以及刻意未动的部分。
- 只把只读的探测命令冻结为检查。会改动东西的命令是工作本身，永远不是 `--check`。

## 双轴评审

凡是产出 diff 或文档的 Run 都要跑两条轴，并保持它们相互独立（见 `engineering-craft.md`）。

1. Standards——是否符合本仓库成文的约定；没有成文约定时，再加上带标签的代码坏味道基线。来源：`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、lint 配置、ADR。
2. Spec——是否忠实于冻结的 `goal`、`scope` 与 `acceptance[]`：缺失或只做了一部分的项、没人要求的工作、看起来完成了但其实不对的项。每条发现都引用验收 id。
3. 在 `--findings-file <path>` 指定的文件里每行写一条发现，每条以所属的轴开头——`Standards:` 或 `Spec:`——并在 `--summary` 里给出每条轴各自的条数与最严重的发现。绝不跨两轴合并或重新排序。
4. 验收项未覆盖的风险——安全、兼容性、数据丢失——即使全部通过也要作为发现记录下来。
5. 评审与 `run verify` 之间不做任何修改。针对旧内容的评审不是针对新内容的证据。

## 评审来源声明

`run verify --reviewer <self|subagent|external>` 记录结论由谁产出。三者都是声明，不是可信证明：Runtime 看不到评审者的上下文，因此只保存这个标签，并在 `verification.md` 中呈现给用户自行权衡。按实际发生的情况声明。

| 取值 | 含义 | 适用场景 |
|---|---|---|
| `self` | 做这项工作的同一个 Agent 会话自己也做了评审 | 单会话 Run 的默认值；如实写明即可 |
| `subagent` | 当前宿主的另一个子 Agent 在独立上下文中做了评审 | 宿主提供子 Agent，且确实有一个评审了 diff 或交付物 |
| `external` | 本会话之外的参与方做了评审：用户、另一个工具、CI、另一个客户端里的评审者 | 结果确实存在、可以引用，并且你说明了它来自哪里 |

- 没有这样的评审者运行过，就绝不声明 `subagent` 或 `external`。夸大的标签比 `self` 更糟。
- 子 Agent 与你共用宿主，通常也共用指令：它带来的是干净的上下文，不是独立性。`external` 的分量只取决于其来源；同一会话里的另一个模型仍然是 `self`。
- 任何取值都不表示"独立"或"可信"。给多少权重由用户决定；Agent 的职责是让用户能够做出这种判断。
- 格式错误的结果不是裁定：Runtime 把它计为一次 verifier 尝试（三次后进入 `await-user`），不计入停滞。

## 什么时候写 `--no-checks-reason`

- 只在没有任何命令能如实判定结果时才写：调研报告、架构评估、产品分析。用一句话给出理由，并说明改为附上什么证据。
- 绝不用它跳过失败、缓慢或不方便的测试。
- 改动代码的 Run 至少需要一条可执行的检查：仓库已有的测试或构建，或为这次改动专门写的聚焦命令。仓库有文档构建或 lint 时，"只是文档"不构成理由。
- 声明了 `no_checks_reason` 而 `.matrix/` 之外的代码又有改动时，`run submit` 返回 `CODE_CHANGED_WITHOUT_CHECKS`。把它当作补一条真检查的要求。补检查需要重新 `run frame`，而 `execute` 开始后这需要用户确认。
- 失败的检查是要修复的失败轮次，不是要删掉的检查。移除或放宽已冻结的检查会改变验收，必须由用户决定。

## `run verify` 之前

- 每个验收 id 恰好有一个结果；每个 `failed` 或 `blocked` 结果都带原因，原因里含 `:` 或 `=` 时走 `--result-file <path>`。
- 每个 `passed` 项都指向一条 Runtime 执行过的检查，或一处读者可以打开的来源。
- 每个 `failed` 项都把原因写到足以直接修复、无需重新调查的程度。
- 评审者取值与实际相符，发现文件里两条轴都在。
